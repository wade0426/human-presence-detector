## 1. 背景與目的

「人體辨識休息提醒系統」透過 RTSP 影像偵測使用者是否在座位上，據此累計連續工作時間並在達到門檻時提醒休息。實測（影片）發現多項與**時間顯示語意**、**提醒內容**、**統計更新**與**背景穩定性**相關的缺陷，導致使用者無法信任畫面上的時間與統計值，背景並持續拋出例外。

本文件定義上述缺陷修正後的**期望行為**與**驗收標準**，作為後續實作與測試的依據。本文件**僅描述需求**，不含實作細節與排程。

---

## 2. 名詞與狀態定義

系統的計時狀態（`TimerState`）與畫面文字（`STATE_TEXT`）對應如下：

| 狀態（enum） | 畫面文字 | 意義 |
|---|---|---|
| `IDLE` | 待機 | 尚未開始或已重置 |
| `WORKING` | 工作中 | 偵測到在場、正在累計連續工作時間 |
| `AWAY` | 短暫離開 | 偵測到離開但未達重置門檻 |
| `REMINDING` | 提醒中 | 連續工作已達門檻、提醒已觸發、人仍在場 |
| `RESTING` | 休息中 | 已開始休息、累計休息時間 |
| `AWAITING_RETURN` | 待機 | 休息達標、等待使用者確認返回 |
| `SUSPENDED` | 已暫停 | 使用者手動暫停偵測與計時 |

關鍵時間量：

- **連續工作時間（work_elapsed）**：自本輪工作開始累計、在場才增加的時間。
- **工作門檻（work_threshold）**：`timer.work_threshold_min`，達此值觸發提醒。
- **超時時間（overtime）**：`max(0, 連續工作時間 − 工作門檻)`，於進入「提醒中」時約為 `00:00`。

## 4. 功能需求

每項需求包含：**現狀與根因 → 期望行為 → 驗收標準**。

### FR-1　狀態列「提醒中」時間語意

**對應報告**：系統錯誤說明報告 #1；BUG-002。

**現狀與根因**
- `status_strip.py` 在非休息狀態一律顯示 `work_elapsed_sec`；`timer_engine.py` 在 `REMINDING` 狀態仍持續累加 `work_elapsed`。
- 結果：狀態由「工作中 00:29」切到「提醒中 00:30」後，時間沿用工作計時繼續累加（如「提醒中 02:08」），使用者無法判斷該數字代表工作、提醒持續或超時。

**期望行為**
- 「提醒中」狀態提供兩種顯示模式，由設定切換（見 §6）：
  - **模式 A：超時（預設）** — 顯示「超時 MM:SS」，數值 = `max(0, 連續工作時間 − 工作門檻)`；進入「提醒中」時約從 `00:00` 起跳，之後隨在場持續累加。
  - **模式 B：工作 + 提醒** — 同時顯示「連續工作總時長」與「本次提醒已持續時間」（提醒已持續時間 = 自進入「提醒中」起經過的在場時間，等同超時時間）。
- 其餘狀態（待機／工作中／休息中／已暫停）的時間意義維持原本對應的量，不因本需求改變。
- 進度條於「提醒中」可維持顯示工作門檻達成度（已達 100%），不影響上述文字。

**驗收標準**
- AC-1.1：預設設定下，由「工作中」切到「提醒中」時，狀態列文字為「超時 00:00」（誤差 ≤ 1 秒），之後每經過 1 秒在場，超時值 +1 秒。
- AC-1.2：切換為「工作 + 提醒」模式後，狀態列同時呈現連續工作總時長與提醒已持續時間，且兩者語意可由標籤明確區分。
- AC-1.3：任何模式下，「提醒中」的顯示數字都不得出現回溯（下一秒小於上一秒）或非預期跳變（單次 > 2 秒的跳動，排除暫停／恢復）。

### FR-2　暫停／恢復顯示語意

**對應報告**：系統錯誤說明報告 #1（暫停數值突變、恢復時間回溯）。

**現狀與根因**
- 報告觀察到：點「暫停」時由「工作中 01:17」瞬間跳為「已暫停 01:42」；點「繼續運行」後出現「提醒中 01:34 → 工作中 01:36」的回溯與前後不一致。
- 根因為暫停／恢復時計時基準（`_last_t`）與顯示值未正確凍結／重設，導致抓到系統時鐘絕對差值或回補了暫停期間的時間。

**期望行為**
- **暫停時**：凍結當下的連續工作時間並持續顯示。例如「工作中 01:17」→「已暫停 01:17」（數字不變、不突跳）。
- **暫停期間**：所有計時停止累加，畫面數字維持凍結值。
- **恢復時**：自凍結值繼續計時，**不回溯、不突跳、不回補暫停期間經過的時間**；狀態回到暫停前的狀態（工作中／提醒中等）。

**驗收標準**
- AC-2.1：在「工作中 mm:ss」按暫停，狀態文字變為「已暫停」，時間數字與暫停前相同（誤差 0 秒）。
- AC-2.2：暫停 N 秒後恢復，恢復瞬間顯示值等於暫停時的凍結值（誤差 ≤ 1 秒），不包含暫停的 N 秒。
- AC-2.3：恢復後連續工作時間單調遞增，無回溯。
- AC-2.4：在「提醒中」暫停再恢復，行為與 AC-2.1～2.3 一致，且恢復後仍為「提醒中」並沿用 FR-1 的顯示模式。

### FR-3　提醒彈窗時間文字

**對應報告**：系統錯誤說明報告 #2；BUG-001。

**現狀與根因**
- `popup.py` 以 `strings.REMIND_BODY.format(minutes=ctx.work_minutes)` 顯示，`REMIND_BODY = "你已連續工作 {minutes} 分鐘。"`。
- `ReminderContext.work_minutes` 為 `int`，且帶入的是**設定門檻**（非實際工作時間）；當門檻 < 1 分鐘（如 0.5）時 `int(0.5) = 0`，故固定顯示「你已連續工作 0 分鐘。」。

**期望行為**
- 彈窗顯示**觸發當下實際的連續工作時間**（而非設定門檻）；重複提醒時，數值應隨實際已連續工作時間更新。
- 時間採**動態單位**格式：
  - 不足 60 秒：以秒顯示，例「你已連續工作 30 秒。」
  - 達 60 秒（含）以上：以分鐘顯示，例「你已連續工作 1 分 30 秒。」（分／秒的中文呈現方式於實作時統一，至少不得再出現「0 分鐘」）。
- 為支援上述內容，`ReminderContext`（或提醒派發流程）需攜帶觸發當下的實際工作秒數，而非僅設定門檻。

**驗收標準**
- AC-3.1：工作門檻設為 0.5 分鐘並觸發提醒，彈窗顯示的時間 ≈ 30 秒（以秒呈現），不得顯示「0 分鐘」。
- AC-3.2：連續工作達 90 秒時觸發／重複提醒，彈窗以分鐘為單位顯示（如「1 分 30 秒」），非「1 分鐘」固定值。
- AC-3.3：重複提醒（`repeat_interval`）再次彈出時，時間數值反映當下實際連續工作時間，較前次為大。

### FR-4　今日工作統計即時更新與完整記錄

**對應報告**：BUG-003；並與 FR-5 相關。

**現狀與根因**
- `today_summary()` 僅統計**已寫入**資料庫的 work session；進行中的工作不計入，故「今日工作」在工作期間維持不變。
- 此外，work session 只在「離開逾時重置」路徑（`AWAY → IDLE`）以 `WORK_ENDED` 寫入；當工作以「進入休息」結束（`REMINDING → RESTING`、`confirm_return`）時**未送出 `WORK_ENDED`**，該段工作時間**完全未被記錄**，造成「今日工作」長期低估。

**期望行為**
- **即時累加顯示**：「今日工作」顯示值 = 資料庫已完成 work session 時間總和 ＋ 目前進行中工作時間（`WORKING` / `REMINDING` 狀態的 `work_elapsed`）。
- **避免重複計算**：當進行中的 work session 結束並寫入資料庫後，進行中部分歸零，總和改由資料庫提供，前後顯示值連續、不重複加總。
- **完整記錄**：所有「已完成的連續工作區段」都需被正確記錄並計入今日工作，包含以「進入休息／確認返回」結束的區段，而不僅是「離開逾時重置」。
- 暫停期間進行中工作時間維持凍結（與 FR-2 一致），不持續累加。

**驗收標準**
- AC-4.1：工作進行中，「今日工作」隨時間持續增加（至少每次畫面更新可見變化），不再固定不變。
- AC-4.2：一段工作以「開始休息 → 完成休息 → 確認返回」結束後，該段工作時間被寫入資料庫，並反映在「今日工作」累計中。
- AC-4.3：work session 寫入前後，「今日工作」顯示值連續、無重複加總造成的跳增。
- AC-4.4：暫停期間「今日工作」不增加；恢復後正常累加。

### FR-5　SQLite 跨執行緒安全

**對應報告**：系統錯誤說明報告 #3；BUG-004。

**現狀與根因**
- `logging_store.py` 已採 **per-thread 連線**（依 `threading.get_ident()` 各自建立）。
- 但 `close()` 會走訪並關閉**字典內所有連線**，其中包含「其他執行緒（如 UI 主執行緒查詢 `today_summary`）建立的連線」；當 worker 執行緒於 `finally` 呼叫 `close()` 時，跨執行緒關閉觸發例外：
  `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`。

**期望行為**
- 維持 **per-thread 連線**架構。
- `close()`（及其他關閉行為）**僅關閉呼叫端執行緒自己建立的連線**，不得跨執行緒關閉或操作其他執行緒的連線物件。
- 系統在正常**啟動、關閉、暫停／恢復、狀態切換**流程中，背景**不得**出現上述未處理例外。
- 紀錄寫入（工作／休息 session、今日統計查詢）在正常運行下不因執行緒問題而失敗或遺漏。

**驗收標準**
- AC-5.1：完整跑一輪「啟動 → 工作 → 提醒 → 休息 → 返回 → 暫停 → 恢復 → 關閉」，背景終端機不出現 `SQLite objects created in a thread...` 或其他未處理例外。
- AC-5.2：UI 主執行緒查詢今日統計與 worker 執行緒寫入 session 可並存，互不關閉對方連線。
- AC-5.3：關閉程式後，由各執行緒建立的連線各自被正確釋放，無資源洩漏警告。

### FR-6　RTSP 串流穩定性與狀態呈現

**對應報告**：系統錯誤說明報告 #4；BUG-005。

**現狀與根因**
- 背景終端機持續輸出 `RTP: PT=60: bad cseq`、`error while decoding MB`、`co located POCs unavailable`、`Stream timeout triggered after 30030.270000 ms`、`libpng error: IDAT: CRC error` 等串流不穩定相關訊息。
- 現有連線徽章（`ConnectionState`：IDLE/CONNECTING/CONNECTED/RECONNECTING/NO_SIGNAL/ERROR）未充分反映「解碼異常／逾時」情形，使用者只能從背景輸出察覺問題。

**期望行為**
- **狀態呈現**：在現有連線徽章基礎上，明確呈現串流不穩定狀態，至少涵蓋「重連中」「收不到影像」，並能反映「影像解碼異常／串流逾時」（可沿用或擴充 `ConnectionState`，例如以 `ERROR`／新增狀態呈現「影像異常」）。
- **自動重連**：串流中斷或逾時時，依 `source.reconnect_interval_sec` 自動嘗試重連，重連期間 UI 顯示對應狀態。
- **降噪**：降低 ffmpeg／libpng 等底層解碼警告對背景輸出的干擾（例如收斂為彙整後的警示或調整日誌層級），避免大量噪音淹沒真正重要的訊息。
- **不崩潰**：串流不穩定（封包遺失、破圖、逾時）時系統不得崩潰，計時邏輯在無有效影像時應合理處置（例如維持上一狀態、不誤判在場）。

**驗收標準**
- AC-6.1：模擬串流中斷／逾時，UI 連線狀態於合理時間內切換為「重新連線中／收不到影像／影像異常」之一，而非僅在背景輸出錯誤。
- AC-6.2：串流恢復後，連線狀態自動回到「已連線」，計時與偵測恢復正常。
- AC-6.3：串流不穩定期間，背景錯誤訊息明顯收斂（不再以原始頻率刷屏），且系統不崩潰、無未處理例外。

## 5. 非功能需求

- **NFR-1 穩定性**：正常啟動、關閉、暫停／恢復、狀態切換流程中，背景不得出現未處理例外。
- **NFR-2 測試覆蓋**：每項 FR 的核心邏輯需有對應單元測試（沿用既有 `tests/` 與 `pytest`），時間相關邏輯以可注入時鐘（如 `clock` 參數）驗證，不依賴真實等待。
- **NFR-3 向後相容**：新增設定（§6）需有合理預設值，既有 `config.yaml` 未含該欄位時系統仍可正常啟動並採預設行為。
- **NFR-4 在地化**：所有新增／修改的對外文字維持繁體中文，與既有 `strings.py` 風格一致。
- **NFR-5 不回歸**：既有功能（偵測、提醒方式、休息判定、ROI、托盤等）行為不受本次修正影響。

## 7. 風險與相依

- **R-1（時間語意一致性）**：FR-1 的「超時」、FR-3 的「彈窗實際工作時間」、FR-4 的「進行中工作」皆源自同一 `work_elapsed`，需確保三者計算基準一致，避免畫面、彈窗、統計互相矛盾。
- **R-2（統計重複計算）**：FR-4 的「已完成總和 + 進行中」在 session 寫入瞬間最易發生重複或落差，需明確定義切換時點（見 AC-4.3）。
- **R-3（記錄路徑變更的副作用）**：FR-4 要求補記「以休息結束的工作區段」，會改變 work session 的產生時機，需確認不影響休息次數統計與既有測試。
- **R-4（執行緒關閉時序）**：FR-5 修正 `close()` 後，需確認程式結束時各執行緒連線都有被關閉（避免只關自己卻漏關他人造成的洩漏）。
- **R-5（串流降噪過度）**：FR-6 降噪不得掩蓋真正需要使用者知道的中斷／逾時事件（與 AC-6.1 平衡）。
