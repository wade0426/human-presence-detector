# Vibe Coding 起始 Prompt — 休息提醒系統功能擴充（全自動・主／子 Agent）

> 這份文件是「主 Agent」的起始指令。把本文件內容作為任務交給一個具備**子 Agent（sub-agent / Task）派遣能力**的 Agent，即可在**完全無人參與**的情況下，依模塊逐一實作、測試、審查並完成整個功能擴充專案。

---

## 0. 你的角色（主 Agent）

你是本專案的**總指揮（orchestrator）**。你**不親自撰寫模塊程式碼**，而是：

1. 讀懂整體工程（需求、設計、任務劃分）。
2. 依依賴順序，**為每一個模塊派遣一個獨立的子 Agent** 去實作該模塊並完成其單元測試。
3. 對每個子 Agent 的成果做**第二階段審查**，通過後才在 `docs/tasks/progress.md` 標記完成。
4. 全程追蹤進度、處理失敗、最後做整合驗證並輸出總結報告。

**整個過程不會有任何人工參與。你絕對不可以停下來向使用者提問或等待確認——遇到不確定時，依本文件的規則自行決策並記錄。**

## 2. 全域鐵則（你與所有子 Agent 都必須遵守）

1. **全自動、不打擾人**：任何情況都不得向使用者提問或等待人工；以本文件規則自行決斷。
2. **TDD**：先寫會失敗的測試 → 跑測試確認失敗 → 寫最小實作 → 跑測試確認通過。
3. **每個模塊都要有完整 pytest 單元測試**，且必須通過：
   - `rtk pytest`（該模塊測試全綠）
   - `rtk ruff check`（無錯誤）
   - `rtk mypy`（無新增錯誤）
4. **完全不碰 git**：不要 `commit`、不要開分支、不要 `add`／`push`／`stash`。只負責改檔、跑測試、更新 `progress.md`。版本控制由使用者手動處理。
5. **嚴守模塊邊界（無越權）**：每個子 Agent 只能改動其 task 檔標頭「異動檔案」所列的檔案。**不得順手改其他模塊的檔案**；若發現需要他人尚未完成的介面，視為依賴未滿足（見 §6）。
6. **向後相容**：既有元件的既有呼叫方式必須維持可用（例如 `ReturnPromptDialog()` 必須仍可零參數呼叫）；新參數一律給預設值。詳見 `docs/detailed-design.md` §1 第 5 點與各 task 檔的相容性註記。
7. **遵循既有風格與規範**：沿用專案既有命名、註解密度、慣例；shell 指令優先使用 RTK 包裝版（見 `AGENTS.md`），並依當前作業系統採用正確語法。
8. **Qt 測試規範**：Qt 元件測試用 `qtbot` + offscreen（`tests/conftest.py` 已設 `QT_QPA_PLATFORM=offscreen`），訊號用 `qtbot.waitSignal`，並標記 `@pytest.mark.qt`；純邏輯用一般 `pytest`。
9. **不真正觸發破壞性副作用**：例如自動測試**不得真的呼叫 `LockWorkStation()`**（會鎖住機器）；一律以注入的 fake（`lock_fn` / `window_factory` / fake player）替換真實副作用。

## 3. 實作順序（依賴拓撲）

依 `docs/tasks/progress.md`「建議實作順序」逐一進行：

```
M0 → M5 → M1a → M1b → M2a → M2b → M2c → M3a → M3b → M3d → M3c → M4 → INT
```

- 每個模塊的 task 檔標頭都有「依賴模塊」欄位；**只有在其所有依賴模塊皆為「已完成」狀態時，才可派遣該模塊的子 Agent**。
- M0 與 M5 互不相依（可先做哪個都行，但建議先 M5 建立乾淨字串／引號基準，供後續新增字串遵循）。
- 開工前請依各 task 檔的「依賴模塊」自行建立一份依賴圖，作為 §6 失敗時「跳過相依模塊」的判斷依據。

## 4. 每個模塊的工作流（核心循環）

對順序中的每一個模塊，執行下列循環：

### 步驟 A — 派遣實作子 Agent

派遣**一個全新的子 Agent**專責此模塊。子 Agent 從零開始、沒有你的上下文，因此你必須在指派時給足資訊。請用以下範本組裝子 Agent 的指令：

```
你是負責實作「<模塊代號，如 M3b>」的子 Agent。

工作依據（請先完整閱讀）：
- 任務清單與完成定義：docs/tasks/<module>.md
- 對應設計章節：docs/detailed-design.md <該模塊的 §X.X>
- 對應需求：docs/proposal.md <該模塊對應需求>
- 專案規範：CLAUDE.md / AGENTS.md

必守規則：
- 嚴格 TDD：先寫失敗測試 → 確認失敗 → 最小實作 → 確認通過。
- 只能改動 task 檔標頭「異動檔案」所列檔案，不得改其他模塊檔案。
- 不得執行任何 git 操作。
- 不得真的觸發破壞性副作用（鎖屏、播放裝置等），用注入的 fake 替代。
- 完成後務必自我驗證並回報下列指令的結果：
    rtk pytest <該模塊測試檔>
    rtk ruff check <改動的檔案>
    rtk mypy <改動的檔案>（若 task 檔 DoD 有要求）

回報內容：改動了哪些檔案、新增哪些測試、上述三項檢查的實際輸出（成功或失敗訊息）。
```

### 步驟 B — 第一階段關卡：測試綠燈

收到子 Agent 回報後，**你自己再獨立跑一次驗證**（不要只信子 Agent 的話）：

```
rtk pytest <該模塊測試檔>
rtk ruff check <改動的檔案>
rtk mypy <改動的檔案>     # 依該 task 檔 DoD
```

- 任一項失敗 → 進入 §6 失敗處理（重試）。
- 全綠 → 進入步驟 C。

### 步驟 C — 第二階段關卡：主 Agent 程式碼審查

你親自審查子 Agent 的實作，逐項確認：

1. **符合規格**：實作的類別／函式介面、簽章、行為是否與該 `docs/tasks/<module>.md` 與 `docs/detailed-design.md` 對應章節一致。
2. **注入點正確**：依賴注入（fake player / `lock_fn` / `window_factory` / 臨時 db / 臨時 config_path 等）是否如設計所述可替換、可測。
3. **無越權改動**：是否只動了 task 檔「異動檔案」所列檔案，沒有偷改其他模塊。
4. **測試有意義**：測試是否真的覆蓋 task 檔列出的案例，而非為了綠燈寫的空殼。
5. **相容性**：是否維持既有呼叫方式（如零參數建構）。

- 審查發現問題 → 視為未通過，進入 §6 失敗處理（帶著具體問題重試）。
- 審查通過 → 進入步驟 D。

### 步驟 D — 標記完成並更新進度

- 在 `docs/tasks/progress.md` 將該模塊那一列由 `- [ ]` 改為 `- [x]`。
- 在對應的需求覆蓋 checklist 若該需求所有模塊皆完成，一併勾選。
- 繼續處理順序中的下一個模塊。

---

## 5. 進度追蹤（`docs/tasks/progress.md`）

你以 `docs/tasks/progress.md` 作為唯一的進度真相來源。狀態標記約定：

| 標記 | 意義 |
| --- | --- |
| `- [ ]` | 尚未開始 / 進行中 |
| `- [x]` | 已完成（兩階段關卡皆通過） |
| `- [ ] 🚫 BLOCKED：<原因>` | 重試耗盡仍失敗，已阻塞（見 §6） |
| `- [ ] ⏭️ SKIPPED：依賴 <模塊> 阻塞` | 因依賴被阻塞而跳過 |

每完成一個模塊或變更其狀態時，立即更新此檔，確保流程中斷後可從這裡接續。

---

## 6. 失敗處理（無人值守的容錯策略）

當某模塊在「第一階段（測試/ruff/mypy）」或「第二階段（審查）」未通過：

1. **有限重試**：對同一模塊，最多重試 **3 次**。每次重試派遣一個**新的子 Agent**（或同一子 Agent 繼續），並**附上具體失敗資訊**（失敗的測試名稱、錯誤訊息、ruff/mypy 報錯、或你的審查意見），要它針對性修正。
2. **重試耗盡仍失敗**：
   - 在 `docs/tasks/progress.md` 將該模塊標記為 `🚫 BLOCKED：<簡述失敗原因>`。
   - 依你建立的依賴圖，將**所有（直接或間接）依賴此模塊的下游模塊**標記為 `⏭️ SKIPPED：依賴 <該模塊> 阻塞`，並不予派遣。
   - **繼續處理其餘與之無依賴關係的模塊**（不要因單一模塊失敗而中止整個流程）。
3. **不可停下等人**：絕不暫停流程詢問使用者；以上規則即為最終裁量。

> 範例：若 `M2b` 阻塞，則 `M2c`、`M4`（其依賴鏈含 M2c）、`INT` 應一併 SKIPPED；但 `M3a/M3b/M3d/M3c`、`M5` 等不相依者仍照常進行。

---

## 7. 整合驗證（所有可完成的模塊都處理完之後）

1. 跑全專案檢查：
   ```
   rtk pytest
   rtk ruff check .
   rtk mypy src cli
   ```
2. 若有失敗，判斷是否源自已標記 BLOCKED 的模塊；若是既有阻塞造成，記錄即可，不需違反 §6 規則強行修復不相干模塊。
3. 勾選 `docs/tasks/progress.md` 文末「整合驗證」中可自動驗證的項目（手動驗收項保留給使用者）。

---

## 8. 最終總結報告（流程結束時輸出）

流程結束時，輸出一份清楚的總結，至少包含：

- **已完成模塊**清單（13 個中完成幾個）。
- **阻塞 / 跳過模塊**清單，每項附原因與重試次數。
- **整合驗證結果**（`rtk pytest` / `ruff` / `mypy` 的最終狀態摘要）。
- **需求覆蓋情形**：五大需求各自是否已全部模塊到位。
- **給使用者的後續提示**：例如「請自行 review 並 commit」、Windows 手動驗收項（音效、清除資料兩入口、強制鎖定三種警示模式實際鎖屏）。

## 9. 立即開始

1. 讀 `docs/proposal.md`、`docs/detailed-design.md`、`docs/tasks/progress.md` 與所有 `docs/tasks/<module>.md`。
2. 依各 task 檔「依賴模塊」建立依賴圖。
3. 從 `M0` 開始，按 §3 順序執行 §4 的工作循環。
4. 全程依 §5 更新進度、依 §6 容錯、最後依 §7–§8 收尾。

開始吧——這是一場無人值守的接力，請穩定、嚴謹、有紀錄地把 13 個模塊一一交付。
